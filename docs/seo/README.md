# TrailFusion AI のSEO運用

開始日: 2026-11-22（日本時間）。対象は https://trailfusionai.com/ とこのリポジトリの公開サイトだけ。

## 目的と公開の境界

実データで既存の検索流入を守り、改善案を少数ずつ検証する。検索順位、インデックス登録、流入増加は保証しない。
2026-11-22、本人が初回PR #3の公開と、今後のこのサイトのSEO改善・採用判断・検証・公開をAIへ委任した。
この範囲では変更ごとの再承認を待たず、根拠を確認して実装から本番確認まで進める。
調査は読み取り専用の仕事として行い、その結果を実装フェーズの判断に使う。
実装ブランチや下書きPRへの保存は、本番公開の完了を意味しない。
`master` への反映で GitHub Pages の公開処理が動くため、最新の差分とCIを確認してからマージする。

この委任は、料金・契約・提供条件・認証権限・計測設定の変更や、メール/SNS等への外部送信の許可を追加するものではない。
既存の事実を一次資料で確認して説明を直すことと、新しい価格・体験・実績を作ることを区別する。
本人にしか確認できない体験など、公開文の正確性に必要な情報が欠ける場合は、その事実だけを確認する。

既存の中学受験・旧単科・DIY・整備のURLを維持する。流入があるURLを、名前が古いという理由だけで削除・統合・転送しない。
海外版の主力アプリと言語方針は `docs/brand/README.md` の最新指示に従う。

## 情報源

| 知りたいこと | 正本 | 誤って代用しないもの |
|---|---|---|
| Googleのクリック・表示・CTR・掲載順位・検索語 | 対象プロパティのSearch Console | GA4セッション、公開PVカウンター、検索ツールの掲載順 |
| サイトへの訪問・入口・ストアへの遷移 | ホストを確認したGA4 | アプリDL数、購入数、検索順位 |
| 現在の公開ページ | 公開URLのHTTP応答とHTML | 未公開ブランチ、古い検索キャッシュ |
| 変更内容と公開状態 | Gitの差分・PR・デプロイ結果 | 予定・AIの完了宣言 |
| ストア掲載数・評価の確認時点 | `docs/brand/store-snapshot.json` | その数字を現在時刻で再確認したという表示 |
| Questの最新集計 | `docs/quest/released-gallery-counts.json` | 古い詳細データの数だけを新しい日付にすること |
| Questの旧単元詳細 | `docs/quest/course-stats.json` の確認日 | 最新集計と同じリリースだという断定 |

APIが返さない値は「未取得」、対象行が返らない場合は「行なし」と記載する。行なしを0にしない。
匿名化された検索語、取得上限、しきい値、未確定日、タイムゾーンによる集計差を記録する。
GA4のユーザー数は期間ごとに取得し、日別やページ別のユニーク数を足さない。
GSCの日次は太平洋時間、GA4は対象プロパティのタイムゾーン。日付ラベルを揃えても同一の時間区間や指標とはみなさない。
Search ConsoleのCTRはクリック合計÷表示回数合計で計算し、行のCTRを単純平均しない。
平均順位の変動は検索語の構成変化でも起こる。順位低下の原因を、平均値だけで断定しない。

## 今回の実装

1. ストア掲載数、教材説明、理科の収録集計、難易度、旧単科アプリからの購入・記録の案内を正本と整合させる。
2. App Storeから転記した評価を、サイト自身が収集した評価としてJSON-LDへ掲載しない。読者向けのストア評価表示と出典は残す。
3. 対訳がないページを英語トップ等へ `hreflang` で結び付けない。正規URL・通常の言語ナビ・実際の対訳同士の参照は保持する。
4. 検査をPRと公開処理に組み込み、再生成で問題が戻ることを検出する。

構造化データを整えても、検索結果の装飾表示は保証されない。実際に収集していないレビューは作らない。

## 再生成後・公開前の検査

```sh
python scripts/brand/check-static.py
python scripts/seo/audit.py
python scripts/quest/content_consistency.py --check
node scripts/add-visitor-counters.mjs --check
node --test tests/visitor-counter.test.mjs tests/global-locale.test.mjs
```

`scripts/seo/audit.py` はサイトマップに含まれる全URLのローカルHTMLを検査する。ネットワーク送信やファイル更新はしない。
タイトル・説明・canonical・noindex・JSON-LD・言語版の戻りリンク・レビューの出典方針を確認し、問題があると終了コード1を返す。
見出し数と同一タイトルは参考警告。JavaScriptで見出しを表示するページや、別言語で自然に同じ表現になる場合もあるため、警告だけで自動修正しない。
HTML検査の合格はGoogleのインデックス登録・選択canonical・表示速度の実測合格を意味しない。

内容を再同期するときは `python scripts/quest/content_consistency.py --write` を実行し、差分と `--check` を確認する。
既存の各生成段階を飛ばした全面再生成は避ける。最新の18教材・海外言語版・ギャラリーを古いテンプレートで上書きしない。
ブラウザ表示を変える修正では、既存の `scripts/brand/validate.py` / `validate-global.py` と対象ページの確認も行う。

## Googleの実データを読み取る

`scripts/seo/collect_google.py` は既存のGoogle認証を使った読み取り専用の集計プログラム。
利用例と正確な引数は `python scripts/seo/collect_google.py --help` で確認する。
対象プロパティのWebストリームとホスト名が一致してから集計する。
認証画面を開く、権限を追加する、課金プランを変更する、別アプリを収集する処理は行わない。

認証ファイル・トークン・個人データ・GA4/GSCの実測レポートをこの公開リポジトリへコミットしない。
実測レポートは非公開のチャットまたはユーザーが指定する非公開の保管先へ返す。
標準出力に出るのは集計結果と安全な取得状況だけ。APIアクセスが拒否されたら、その情報源を未取得として扱う。

GA4とSearch Consoleのアクセス権は別々に確認する。Googleの認可済み状態だけでなく、プラグインで選択された対象サイトと利用枠も確認する。
`collect_google.py` のSearch Console機能は期間合計の取得まで。ページ別・検索語別の分析には、利用できる専用コネクターかSearch Console本体の表示・エクスポートを使う。
ブラウザから読む場合も、プロパティ、期間、検索タイプ、各種フィルター、最終更新日、エクスポートの行数制限を確認する。アクセスできる他サイトへ対象を広げない。
追加認可が必要な場合はGoogleの正式な認可画面を使い、既存の共用認証を書き換えない。接続と実データが確認できるまでは、掲載順位や検索語の数値を報告しない。

## 毎日の運用

毎朝1回、最新の完了した日付に基づく直近7日と前7日を比較する。GA4コレクターの標準終了日は実行日の日本時間から3日前。別の終了日を指定した場合はその日付と理由を記録する。
対象期間と取得時刻を毎回書き、遅延処理で後から変わる可能性を残す。

Search Consoleが接続できたら、ページ別・検索語別に次を満たす変化だけ報告する。

- クリック差の絶対値が **5を超える**。
- または両期間とも **300表示以上** ある行で、平均順位差の絶対値が **3を超える**。
- 候補が多すぎる場合は重要な3件に絞り、残りの件数を添える。
- 取得漏れ・匿名化・欠落行を確認し、原因は「確認できた事実」と「仮説」を分ける。

GA4は別の指標として、自然検索セッションと `click` イベントのストアドメイン別件数を見る。
自然検索セッションの変動が **10を超え、かつ30%以上** の場合を初期の通知目安にする。これはサイト規模に合わせて調整する運用ルールであり、Googleの基準ではない。
ストアクリックは `apps.apple.com` / `play.google.com` に限定したイベント数。DL・人数・購入とは呼ばない。
`brand_store_click` / `quest_store_click` / `store_click` を検証なしで合算しない。

重大な変化も実施した修正もなければ「確認範囲で大きな変化なし」の1行。修正した日は変更内容・検証・公開結果を添える。取得不能は「変化なし」に置き換えない。
同じ未接続理由の長文通知を毎日繰り返さず、週報に対応待ちとしてまとめる。

## 月曜の週報

1ページ相当の同じ形式で、次を提示する。

1. 対象期間・取得時刻・情報源。GSCのクリック/表示/平均順位、GA4の自然検索セッション/ストア遷移を別々の表にする。
2. 大きく動いた3ページ。前後の数字、確認できたこと、未確認のこと。
3. **実施・見送り・事実確認事項を最大3件**。対象URL、変更前後の具体的な文章や設定、根拠の数字または確認した技術不整合、判断理由、検証・公開結果。
4. 前週に公開した変更とその観察結果。公開前の変化を修正の成果にしない。

最初の月曜には過去90日の上位ページと候補キーワードも確認し、次に着手するテーマを1つ選ぶ。
既存ページで答えられる語は新記事を重複作成せず、該当ページの改善候補とする。

## 5つの仕事用プロンプト

各仕事は別の新しい会話または新しい実行として行う。以下の共通条件を必ず付ける。

> 対象は trailfusionai.com。数値は今回取得した対象サイトのSearch ConsoleまたはGA4から出し、情報源と期間を明記してください。取得できない数値は未取得とし、推定で埋めないでください。データの不整合は再取得して確認してください。この調査ではサイト・設定・公開状態を変更せず、提案と下書きを返してください。その後は本人から委任されたAIが、この運用書の実装・公開手順に沿って採用判断と公開まで進めます。

### 1. 既存の成果を調べる

> Search Consoleの過去90日・全ての国について、クリック上位10ページをクリック・表示・CTR・平均順位付きで示してください。表示が多くクリックが少ない検索語を最大10件、条件を満たす実在行だけで別表に示し、その検索語が表示するページを紐付けてください。条件を満たす行が10件未満なら、その件数のまま報告してください。守る3ページと最初に改善する3ページを、根拠の数字付きで1行ずつ示してください。プロパティ単位・ページ単位の集計差、匿名化や取得上限による検索語の欠落を区別し、ページ/検索語の行合計をサイト合計に代用しないでください。Search Console未接続ならこの順位判定は保留し、GA4の自然検索入口ページを別表として出してください。

### 2. 次の検索語を選ぶ

> サイトマップと公開本文を確認し、読者の利用・購入判断に近い候補検索語を10件探してください。日本向けアプリページと海外向けページは分けて考えてください。既存の該当ページ、検索意図、今回確認した検索結果の競合を示してください。月間検索数・難易度は専用の実測データがある場合だけ書き、取得日と地域を付けてください。検索サービスの返却順をGoogleの確定順位と呼ばないでください。既存ページとの重複を除き、1件だけ提案してください。

### 3. 記事・ページの設計図を作る

> 対象URLと主要検索語を実データから確認し、その語の現在の上位候補ページを5件読んでください。読めなかった本文は未確認としてください。読者が求めることと現行タイトルの一致を先に確認し、新title・meta description・主見出し・見出し順・答える質問・既存ページからの内部リンク3件を1画面で提案してください。未確認の実機検証・料金・体験は、執筆前の質問として残してください。

体験・価格・対応端末等は、既存の一次資料または本人の回答で確認した事実と設計図に沿って下書きを作る。本人にしか分からない未確認事項がある場合のみ確認する。試していないものを試したと書かない。

### 4. 朝のチェック

> 最新の確定データで直近7日と前7日をページ別・検索語別に比較してください。クリック差が5超、または両期間300表示以上かつ順位差3超の行だけを重要順に最大3件示してください。平均順位の変化は検索語の構成と主要検索語の順位を分けて説明してください。変化なしなら1行。行なし・取得不能・実測0を区別してください。GA4は別欄で自然検索セッションとストア外部クリックを比較してください。

### 5. 月曜の週報

> この運用書の月曜形式で、数字、大きく動いた3ページ、実施・見送り・事実確認事項を最大3件、1ページにまとめてください。変更案は対象URL・変更前後・根拠・検証方法を明示し、実施済みならPR・デプロイ・本番確認の証拠を付けてください。前週の公開済み変更がまだ観察できない場合はそのまま書いてください。対象サイト以外の一般論は省いてください。

## AIが担当する実装・公開

今回のPRは「掲載情報の整合」「構造化データ」「言語版の関係と検査」の3群でレビューする。
以後のコンテンツ改善は一度に最大3ページずつ選び、同時に多数のタイトルを変えない。検索意図・既存流入・根拠を確認できたタイトル変更や記事改善は、委任された範囲で公開まで進める。

1. 最新の `master`、公開ページ、調査結果を照合し、変更前後・根拠・検証方法を決める。根拠が不足する案は見送り理由や必要な事実確認を残す。
2. 他作業の未コミット差分を保全し、専用ブランチまたはworktreeで実装する。差分を確認し、PRに変更内容と検証結果を記録する。
3. 対象変更に必要な検査と既存CIを通す。マージ直前に最新head・base・CIの対応を確認し、競合や別変更があれば解消して再検証する。リポジトリ保護や必要レビューを迂回せず、本人や独立レビュアーの承認を偽装しない。
4. 検証済みのheadを指定してマージし、既存のGitHub Pagesデプロイ成功を確認する。公開URLのHTTP応答、反映した内容、canonical/noindex、関連する表示・導線を確認して完了とする。
5. 公開日時・PR・デプロイ・本番確認結果を報告し、翌日以降は実データで観察する。公開不備があれば今回の変更に範囲を絞って修復または差し戻し、再検証する。

URLの削除・統合・転送は流入保護の方針を守り、SEOのためという理由だけで実施しない。
GA4のキーイベント設定や計測イベント統一は今回の委任範囲に含めず、現在の計測との比較が切れない設計を別途提示する。
